# Skill Layer Resolution

**Current:** 2026-10-29

## Requirements

| # | Requirement | Meaning |
|---|---|---|
| R1 | One layer model | The four skill roots, their precedence and their direction are stated once and every doc names the same four |
| R2 | The runtime is the authority | A name resolves the way pi's loader resolves it, observed through the loader rather than a committed prediction |
| R3 | The boundaries fail closed | A collision, a skill the loader does not load and a shipped skill that links outside its own layer are hard findings |
| R4 | The map is a view | The inventory is generated at check time and not committed; the source facts stay in the provenance lockfile |
| R5 | The project is the integration layer | A project skill may link into a shipped layer; a shipped skill may not link out of its own layer |

## 2026-10-29 -- Four layers, generated from the runtime

**Decision:** The skill system has four layers, highest precedence first: **project** (`.agents/skills/`, `/home/agentuser/sandbox/.agents/skills/`), **provider** (`src/reasoning/providers/pi/config/agent/skills/`, `$AGENT_HOME/agent/skills/`), **agent-sandbox** (`src/reasoning/agent/skills/`, `/opt/workflow/agent/skills/`) and **workflow** (`workflow/coding-agent/skills/`, `/opt/workflow/agent/modules/coding-agent/skills/`). A name held by more than one layer resolves to the earlier layer, because pi discovers project and user roots before package resources and the package list orders the agent root before the module root. The resolution is generated by [`scripts/skill_map.mjs`](../../scripts/skill_map.mjs) with pi's own `loadSkills`, and [`scripts/check_skill_map.sh`](../../scripts/check_skill_map.sh) runs it as a lint gate. The map is printed, never committed.

The access rule is one-way. A shipped layer -- provider, agent-sandbox or workflow -- is self-contained: a relative Markdown link in its skills must stay inside that layer's source root. A project-layer skill may link anywhere in the project tree, including into a shipped layer, because the project tree is where the project layer is read. The map reports the allowed project-to-shipped links as a count and fails a shipped link that leaves its root.

A name collision, a discovered `SKILL.md` that pi does not load, and a broken relative link are hard findings. The map warns when a frontmatter name differs from its directory, and when an agent-sandbox skill has no maintenance record; the record's backfill is a roadmap task, not a condition of the layer model.

The four layers are stated in [`agent_workflow.md`](../reference/agent_workflow.md#skills-and-prompts-layer-model), [`provider_lifecycle.md`](../reference/provider_lifecycle.md#how-the-four-layer-skillsprompts-model-interacts-with-this-split) and [`skill-conventions.md`](../../.agents/skills/instruction-authoring/references/skill-conventions.md). The project layer is pi's `.agents/skills` auto-discovery; the other three are `cells` rows in [`container-interface.json`](../../src/build/container-interface.json).

**Rationale:** The docs described three layers and merged the two package roots into one "sandbox" layer, while the runtime held four roots with a different owner for each. The project layer, the highest-precedence root, was absent from the model, and the agent-sandbox and workflow module roots were treated as one even though a module can be absent or can shadow a base skill. A committed resolution manifest would be stale the moment a root, a package entry or the loader order changed; the loader already reports collisions and already knows the order, so the map asks it instead. The access rule follows the runtime: a shipped skill is read from `/opt` or from the provider home, where the project tree and the repository are not present, so a link out of its own layer cannot resolve; a project skill is read from the repository, so a link into a shipped source is a real path in the same tree. The distinction is one rule, not a table of exceptions.

**Rejected alternatives:**

### Keep the three-layer model

Rejected on R1. It merges the agent-sandbox and workflow roots, which have different package entries and can be present independently, and it omits the project layer, which has the highest precedence. A collision between the project and provider layers would be described by a model that does not contain one of them.

### Commit a resolution manifest

Rejected on R2. The manifest is a prediction of what the loader will do; a new package entry, a new project root or a loader change would make it wrong with no gate reporting the drift. The generated map reads the loader at check time, so the prediction cannot be stale.

### Hard-fail every cross-layer link

Rejected on R5. The project conventions deliberately reach into the workflow runbooks and the base skills, and that is the integration the project layer exists for. Treating it as a defect would force copies of those rules into the project or remove the links that make the conventions useful. The direction is the rule, not the crossing.

### Read precedence from the docs

Rejected on R2. The docs are the model a reader needs, not the authority on what the loader does. A knowledge test that only restated the docs would canonize a bug; the inventory calls `loadSkills` and the knowledge test observes the same first-wins rule.

### Put the source revision in the map

Rejected on R4. The map is a view that changes with the runtime; the upstream URL, revision, license and import commit cannot be regenerated from the tree. They stay in the committed provenance lockfile, and the map names the skill's layer, not its source.

**Edge cases / drivers:**

- **A provider-specific layer.** The provider source is the pi config tree because the loader is pi's. A second provider with a different loader would add its own layer row and its own probe; the map does not pretend the four roots are provider-neutral.
- **The project layer is auto-discovered.** Pi reads `<project>/.agents/skills` without a settings key, so the layer is not one of the three `cells` rows. The map names it from the project root; the container interface declares the surfaces an image carries, and the project tree is the session's.
- **Two package roots at one rank.** The `packages` list orders `/opt/workflow/agent` before the module root; a name in both resolves to the agent root. The map's layer table keeps the two roots separate so a module shadow is visible rather than folded into "sandbox".
- **Nested `SKILL.md`.** Pi stops at a directory that holds `SKILL.md`; the runbook files under a skill are content, not skills. The map discovers with the same rule, so a nested file does not appear as a phantom layer member.
- **Links in examples.** A link inside a fenced code block or an inline code span is documentation, not an access edge; the map ignores it. A prose link that leaves a shipped layer is the finding.
- **A missing target.** A project link that does not resolve is a broken link, not an allowed cross-layer link; the map checks the target before it classifies the layer.
- **A collision the layers intend.** The map fails every collision. A deliberate shadow would need a declared exception, and the current tree has none; the gate stays strict until a real case earns the exception.
