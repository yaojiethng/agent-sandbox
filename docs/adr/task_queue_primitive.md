# Task-Queue Primitive

**Current:** 2026-10-01
**Status:** active

## Framing

The task-queue is a **durable exactly-once processing pipeline over break-point messages**, with one deliberate break from the pipeline model: the operator gate. The queue, its state journal, and its single-atomic-write transitions give exactly-once delivery (R1), idempotent keyed consumption by request id, and an atomic outbox per transition. The break is the operator-as-synchronous-bottleneck join: the pipeline is headless and never pauses for a human decision, where this primitive pauses at every worker break point for the operator's release. We borrow the queue, ordering, and durability semantics from process-once pipelines; we do not borrow the automated processing model. (Recorded as the agreed framing from the round-2 surface design, 2026-09-30.)

## Requirements

| # | Requirement | Meaning |
|---|---|---|
| R1 | Durable exactly-once queue | A break point enters the queue exactly once and is dequeued exactly once (I1, I5) |
| R2 | Order preserved per task | Break points trigger in request order per task (I2) |
| R3 | Legal transitions only | A break point moves requested -> scheduled -> triggered, only in that order (I4) |
| R4 | Single-writer on the main tree | No worker's write lands in the main tree except through the primary's bring-back (I6) |
| R5 | File-set bring-back | The bring-back writes exactly the file set the primary names over the write-back proposal: a subset, or the empty set (I7) |
| R6 | Audit at termination only | The termination audit runs only at the worker's terminal break point, before any bring-back (I8, I9) |
| R7 | Worktree hygiene at clean close | Every worktree and branch is pruned by its bring-back or swept at a clean, resumable close (I10, I13) |
| R8 | Single atomic transition | Each transition is one atomic write; a crash leaves the queue resumable at the prior state (I11, I12) |
| R9 | Structurally atomic | I1/I4/I5 hold by construction, not by enforced checks |
| R10 | One blocking join | A break point is delivered by one blocking call; the queue rests only in triggered |
| R11 | Fork owns the worktree location | The worktree path is derived from the run and the task, cut outside the main tree |
| R12 | Transition table as single source of truth | One explicit from-state x action -> to-state matrix states every legal transition of the task lifecycle and the queue entries; the suite walks it, and the prompt's state map documents the same table phase by phase against the loop step each phase runs |
| R13 | One primary per state directory | One state directory has one primary; every state-mutating call is one locked load-derive-save, and a second process is refused with its owner named (2026-10-01) |
| R14 | Task phases | A task has four phases - forked, active, terminated, retired - and the audit is the record that routes a task out of active; the prompt's state map names what each phase means and the step the primary runs in it (2026-10-01) |

Label traceability: the earlier surface labels S1 and S2 name the same two decisions as R10 and R12 with R14. S1 is the one blocking join; S2 is the documented state map, and the transition table and the prompt's state map are its one implementation. R is the label set this ADR carries.

## 2026-10-01 -- The task lifecycle, the fused bring-back, and the ownership lock

**Decision:** The task lifecycle has four phases: `forked`, `active`, `terminated`, `retired`. The termination audit is a task record with two outcomes. A `usable` audit moves the task from `active` to `terminated`; a `not-usable` audit leaves it `active` and is answered by a re-queue, never by a second audit of the same terminal break point. A re-queue has two routes, and the primary picks one by where the damage is: `in-place` rolls the worktree back to the head the last delivered segment reached and keeps the worktree, the branch, and the same worker; `fresh` force-removes the worktree and the branch and cuts a new one from the baseline, reseeding the worker's request sequence. The bring-back is one call: it writes the file set the primary names, which may be the empty set, then removes the worktree and prunes the branch, and that call is what retires the task. There is no separate retirement step and no separate verdict object; the file set is the verdict. Every state-mutating call runs its whole load-derive-save under a file-level ownership lock at `stateDir/ownership.lock`, taken with `O_EXCL`, and the git work the call must not interleave with another's - the fork's cut and undo, the re-queue's rollback, and the bring-back's write - runs inside the same critical section as the record it leaves. A lock is broken when its owner is dead or when its heartbeat is older than 30 s, and the owner beats at each git step inside its section, so a section that outlives the bound keeps its lock while it is alive. The bring-back asks the prune's refusal before it writes: a worktree that still holds content outside the protocol directory refuses the whole call while the main tree is exactly as it was, and the empty file set archives nothing. The prune asks the same question again after the write. That second check is the only refusal left that can follow a write, it needs a worktree that grew content in between, and a worker that stopped at its request does not grow one. A bring-back is the transactional-outbox operation of the primitive, so it records its own intent: inside the locked section and before any git work it writes `stateDir/bringback/<taskId>.json` naming the file set, marks that record once the write or the archive completed, and deletes it in the same section that writes the state record. A terminated task whose worktree and branch are gone is therefore resumable only on that record: a re-run without it is refused with `bring-back-unprovable`, a re-run whose file set differs from the record's is refused with the same code, and the empty file set claims `archived` only when the archived diff exists. A gone worktree is never on its own the evidence, because the operator can remove a worktree and a branch with the two commands the fork refusal prints, and a call that refused at the prune gate leaves a gone tree behind with no write either. A critical section's body is synchronous by construction, checked at compile time and refused at runtime, because the lock is released when the body returns and an await would release it early. A re-queue records the break point it answered, so the join's hold stops naming the re-queue the primary has already taken and waits for the worker's next request; the audit itself stays on the record. The scoping is one primary per state directory: the lock serializes writers, it does not make two primaries on one directory a supported configuration.

**Rationale:** The seven-phase surface made the primary choose between naming a phase and doing the work, and two of the choices were indistinguishable at the moment of decision: a failed verification and a discarded track both ended in a phase that only a verdict could have produced. Four phases remove the states that carried no work, and the audit record replaces them with the one thing the decision depends on - whether the return arrived as directed. Fusing the retirement into the bring-back removes the window where a task's content was in the main tree and its worktree still claimed it, and it makes the crash recovery legible: the prune precedes the record, so an attempt interrupted between them is completed by a re-run that reads what the attempt wrote instead of re-deriving content it can no longer read. A gone worktree cannot carry that evidence on its own, because the same predicate an interrupted attempt satisfies is satisfied by any removal that was not the tool's own prune, and a false record there is worse than no record: it retires a task whose content never reached the main tree. The intent record is the smallest thing that separates the two, and it is written and deleted in the section that owns the write, so it exists exactly across the window it has to cover. Holding the lock across a synchronous body is the same kind of claim: true of every derive today, but unenforced until an async body releases the lock at its first await and two writers interleave on one state directory. The hold after a re-queue points at a step the primary has already taken, which costs no invariant and misleads the operator gate on every re-queue; recording the answered entry moves the hold to the segment the worker has still to run. The empty file set makes declining to bring content back an ordinary call rather than a special verdict, and the branch diff it archives keeps the declined work readable. The re-queue routes separate two failures that one repair mechanism cannot: a segment whose content is wrong is repaired by a rollback, and a worktree whose git state or environment is poisoned is not, because a rollback carries the damage forward. A file-level lock closes the only window the in-process mutation queue left: two processes on one state directory, each loading, deriving, and writing, where the second write silently dropped the first's break point. The lock reports the live owner instead of racing it, and a lock whose owner is dead is broken, so an interrupted run resumes instead of deadlocking.

**Rejected alternatives:**

- Keep the retirement as a separate step after the merge: rejected because it made the worktree's fate a second call the primary could forget, and because a crash between the two left content in the main tree with its worktree still registered. The fused call has one gate, one transaction, and one record.
- Keep the all/partial/none verdict object with a `none` that discards: rejected because `none` is a file set, and a three-valued object made the common case - exactly the paths the operator named - a second encoding of the same decision. The empty file set is the same decision with less surface.
- One repair mechanism (always roll back): rejected because a poisoned worktree survives the rollback. The fresh route exists for the locus of the damage the in-place route cannot repair, and its forced removal is why the branch is packaged first.
- Infer the interrupted bring-back from a gone worktree alone: rejected. The predicate an interrupted attempt satisfies - no worktree, no branch - is satisfied by any removal that was not this tool's own prune: an operator's `git worktree remove --force` and `git branch -D`, which is the remediation the fork refusal prints, and an `rm -rf` of the worktree root. A record built on it retires a task whose content never reached the main tree, and the file set is unrecoverable afterwards. One file, written before the write and deleted in the section that writes the record, is what separates this tool's removal from any other one.
- An advisory lock (`flock`) or a lock directory: rejected. The state directory is already on a local filesystem, `O_EXCL` is the test, and the lock file carries the owner metadata - pid, session, task, worktree, start, heartbeat - that makes a crashed writer's directory readable. A lock directory hides that metadata and a `flock` disappears with the process, which is exactly the case the takeover has to survive.
- Two primaries on one state directory, serialized by the lock: rejected as a configuration the lock would make look supported. One state directory is one run, and one run has one primary; the lock is the guard rail for an accident, not a mode.
- A formal state-machine tool or a generated transition table: rejected. The table is one typed constant and its consumers are lookup helpers, which is the same single source of truth with no build step; the suite walks the table rather than the code, so a row cannot be added without the machine check noticing.

**Edge cases / drivers:** A `not-usable` audit of a break point that is later re-queued leaves the old record and the new entry in place: the exactly-once identities of the queue entries hold across a re-queue, because a re-queue is another segment and not a second run. The in-place rollback carries the protocol directory across the reset, so the worker's request sequence does not restart over ids the run already recorded. The fresh route seeds the worker's request counter at the sequence the queue reached, for the same reason. A bring-back of the empty file set writes nothing into the main tree, archives the branch diff into the run record, and prunes like any other. A bring-back re-run on a retired task reports the recorded result and changes nothing, which is the one call that answers twice. A task whose worktree is gone but whose state still says `terminated` is completed by the re-run, because the prune precedes the record; the record infers the write the intent record names and says so with `resumed`, so a reader tells an inferred record from a performed one. The same state with no intent record is refused instead: the removal was not this tool's prune, the write is unproven, and the refusal leaves the state, the main tree, and the journal exactly as they were. An intent record whose write never completed is refused the same way, which covers a call that stopped at the prune gate before its write. A re-queue leaves the not-usable audit on the record and records the entry it answered, so the hold a later join reports names the worker's next request rather than the re-queue the primary already took. A lock left by a killed writer names the process that held it; the next acquirer reads that metadata, breaks the lock, and finishes its own write. A lock whose owner is alive is reported, not broken, and the message names the owner. A live section longer than the 30 s stale bound beats at its git steps, so the bound measures a silent writer rather than a slow one. A section whose body is a promise is refused at once, at the load-derive-save that would have written past the released lock, and the refusal is the same code the corrupt state uses: the lock's guarantee is that a section is synchronous, and a promise cannot keep it. A worker that runs past its terminal request leaves a document the queue can never admit; the scan names the document and the phase that closed the task, because no other part of the payload can.

## 2026-10-01 -- Confirmation review of the lifecycle bring-back and lock

**Decision:** The round-2 changes converge. The independent confirmation review reproduced each fix in the load-derive-save path (not in the comment layer) and walked the exactly-once edge catalog against the repaired queue: all ten edges hold, including the idempotent-sink edge that the resumed-path inference previously broke. All core invariants hold; the D2/D5/D7/D8/D9 findings stand as scheduled non-blocking repairs. Two recorded trades and one label clarification below.

**Label clarification:** `T1` (no value judgement) and `S2` (documented state map) are not literal labels in this ADR. Their intent is carried by the R-set: R14 is the four-phase lifecycle with no value fork, and the transition table (R12) together with the prompt's four-phase state map is the one implementation of the documented state map (the S1/S2 traceability line). The verification audit's usable/not-usable outcomes are structural findings about the return, never a grade.

**Recorded trade (review finding 6):** a refused bring-back on a `terminated` task whose worktree and branch are gone with no intent record leaves a run no registered tool can close cleanly; the recovery is the documented hand move of the state directory or a package restore. This is deliberate: the alternative is the false record the intent record exists to prevent, and the refusal is the honest minimum.

**Recorded non-blocking repairs (review findings 1-2):** a retired task with a surviving worktree must refuse a different file set unless it matches the recorded set (finding 1); the post-re-queue hold's `requestStatus` should come from the answered entry's status to avoid self-contradiction (finding 2). Both are follow-on rows, not round-2 blockers.

## 2026-09-30 -- The fork and join surface

**Decision:** The operator-driving surface is fork and join. `taskq_join` is the single blocking call through which the primary waits for a worker's break point and handles it: one call scans the task worktrees, records the worker's request, schedules it, triggers it, and returns the join payload, as one pure state derivation applied as one serialized write. The `poll`, `record`, `schedule`, and `trigger` tools are gone, so the intermediate break-point states are not a surface the primary can drive, and the state file never rests in them. `taskq_fork` owns the worktree location: the path follows from the run id and the task id, sits outside the main tree beside it, and a leftover at that path is refused with the path named.

**Rationale:** The four-call driver chain was mechanism the primary had to sequence, not a decision it made. Every intermediate tool was an opportunity to call out of order, and the absence of a wait left the primary polling or sleeping in a shell loop. One blocking call removes that surface by construction, and the atomic derivation keeps exactly-once (I1, I5), the request order per task (I2), and the single atomic write (I11) as properties of the transition rather than of the caller's sequence. A hold - a delivered break point the operator has not decided - is the one piece of state the join reports without delivering, because the operator's decision is the one thing the queue must not take. The derived worktree path removes the observed ergonomic failure (a caller who pre-cut a worktree met branch-exists) and keeps two runs of one repository off each other's paths.

**Rejected alternatives:**

- Keep `poll`, `record`, `schedule`, and `trigger` as advanced or deprecated tools: rejected because every one of them is a way to create a break point the join then has to heal, and the heal path is a state a real caller should never reach. The pure operations remain as internal units with their own tests, so the state machine is still testable without a tool surface.
- Sleep-and-re-poll as the documented wait: rejected. A timed wait is the correct primitive; the scan interval belongs inside the call, not in the caller's loop.
- A `worktree`-root inside the main tree (`<repo>/.worktrees/<task>`): rejected as a conflict with the single-writer rule - a worktree inside the main tree dirties the tree the merge gate reads, and the main tree is never written by a fork. The canonical root is a sibling of the repository, named from the repository and the run id, exactly as the state directory is.

- Adopt a formal-verification toolchain (TLA+/Alloy/Crucible-style) for the queue: rejected. The primitive holds the single-atomic-write and single-primary invariants by construction (structural atomicity, R9), and its correctness target is exactly-once delivery over a single-state-directory queue, not multi-writer consensus. A formal tool at this scale adds an unmonitored surface against the install-nothing/minimal-discipline; it would certify an invariant set we already hold by construction. Formal references (e.g. AWS's TLA+ work on SQS, exactly-once stream-processing catalogs) are consulted as an edge-case checklist against I1-I13 in review, not adopted as a toolchain.
- Adopt a streaming/message-broker framework as the implementation: rejected. It brings the automated, headless processing model the operator gate deliberately breaks; a broker dependency contradicts the minimal pi-extension and plain-files worker protocol.

**Edge cases / drivers:** A timeout is a result, not an error: it consumes, schedules, and triggers nothing, and the next join delivers normally. An abort returns without consuming. A worker request that lands while a join is in flight is delivered on the next call, never lost and never doubled. A state written before the join existed can rest in `requested` or `scheduled`; the join finishes the transition for it. A worker that requested again before its hold cleared is delivered in request order, and the join names the race in the payload notices. Cross-task selection is the primary's choice through the named `taskId`; inside a task the earliest request wins (I2).

## 2026-09-29 -- The general sequencing primitive

**Decision:** task-queue is a general sequencing primitive (fork / operator-synchronous join / re-queue) in `src/reasoning/agent/prompts/`, implemented by the Track B TypeScript pi-extension (`src/reasoning/providers/pi/config/agent/extensions/task-queue/`). It owns the fork procedure, the join, the re-queue rule, the write-back proposal construction, the single-writer rule, the final per-track verification, the verdict-scoped merge, and the records. It does not own a task shape; a caller supplies segmentation and well-formedness. The unit of fork-and-join is the segment ending at a worker-requested break point. The queue records only requested break points and does not mark their kind; final-versus-regular is the primary's dequeue-handler decision. Durability is per-run-state: one `state.json` outside the main tree holds the queue, task records, and the exactly-once request map; operations are pure functions, so I1/I4/I5/I11 hold by construction.

**Rationale:** The primitive must separate the sequencing mechanism from the task shape, which the coupled `parallel-auto` prompt blurs. A segment-based fork/join/re-queue model lets the operator's decision rate pace the wall clock and breaks the mechanism at arbitrary points in a task's lifecycle. A durable, exactly-once, single-atomic-write queue is the load-bearing form: the two independent thermo-nuclear reviews converged on non-atomic transitions and non-resumable close as the blocker, so I11-I13 are first-class rather than an afterthought. Single-writer discipline and verdict-scoped bring-back make the acceptance judgement clean and structural. TypeScript holds the invariants by construction and makes them unit-testable as pure functions, which shipped the invariant set far earlier in a reviewer PASS than bash.

**Rejected alternatives:**

- Track A (bash): rejected for the durability and maintainability wall-clock -- 8 repair rounds (plus the initial review) chased I7/I11-I13 through bash's non-atomic state, a temp-file crash wedge every reader read as a queue entry, a committed-deletion resume gap, an unchecked `reset --hard`, and a rebuilt residue recognizer. Bash offers no enforced module boundary, so safety came from reviewer-discovered fixes, not the language (execution). Retained behind a nushell-revisit row.
- Adopt `pi-subagents` as the primitive: rejected because it implements a different mechanism (delegation to child Pi sessions sequenced by a JavaScript script in one tool call), holds no queue-class invariant I1-I5, and never writes a worker patch into the main tree, so R5 (I7), the invariant the primitive exists to serve, is unreachable by adoption (intent). Its worktree engine's patch-capture-before-removal and fail-closed rollback are adopted as adjacent follow-ups, and the package stays usable for delegation.
- A coupled `parallel-auto`-style task-shaped prompt without a separate primitive: rejected as the defect itself -- it mixes fork, task shape, and gating contract in one prompt (intent).

**Edge cases / drivers:** The acceptance judgement at the final break point reuses the same join as a regular break point, with a terminal verdict added. The bring-back scope (all/partial/none) is validated as a subset of the write-back proposal; a partial verdict must name a non-empty subset held by the proposal. Same-worker re-queue maps to pi's `--continue`/`--fork` on the same session log and directory, so "same worker" and "fresh dispatch on the same log" are the same agent state by construction. A task with no defined break points is a single-segment task that runs to completion. The open interface ergonomics - the missing first-class wait, the under-documented fork `workdir` contract, and the state surface exceeding the conceptual five-state loop - are closed by the fork and join surface above.

**Reason superseded by 2026-09-30 and 2026-10-01:** The seven-phase lifecycle, the verdict object, and the separate retirement are replaced by the four-phase lifecycle, the file-set bring-back, and the fused retirement. The reasoning above stands: the primitive is general, the break point is the unit, and the queue holds exactly-once by construction.
