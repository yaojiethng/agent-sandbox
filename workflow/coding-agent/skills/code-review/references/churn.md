# The churn survey

A churn count quoted without the method behind it cannot be re-derived, so a later reader measures different numbers for the same files and the two cannot be compared. The pass produces a ranking a reader can act on and reproduce. It states the outcome and not the steps (`$AGENT_HOME/agent/skills/communication-principle-state-intent-delegate-method/SKILL.md`), so a run that reaches the same ranking by another route satisfies it.

## The outcome

1. **A ranked measure of how often each tracked file moves.** Every tracked file carries a commit count under one stated window, ranked, so two runs can be compared.
2. **A count that survives reorganisation.** A file's number covers its whole history, including the names it held before a rename, so a reorganised file does not read as quiet.
3. **Two kinds of movement, reported apart.** Each file reports how much of its count is mechanical and how much changed behaviour, so active design is distinguishable from a repo-wide sweep passing through.
4. **A short list a reader can act on.** The deliverable is the files that both move often and carry findings, joined to the findings register. A documentation file joins only through a documentation finding, and its remedy is a documentation edit. Where no register is current, the ranking stands alone and the join waits.
5. **Decisions, not a copy.** The run ends in roadmap candidates, each naming the finding it would fix and the command, window and revision that produced the ranking. The counts are derived on read and are not committed: a consumer re-runs the recorded command rather than trusting a stored table.

## Trusted only when

- **Every number is re-derivable.** The record carries the command, the window and the revision it measured; a count without them is not comparable and is not reported.
- **The split is honest and conservative.** A behaviour change is never counted as mechanical, uncertainty resolves to functional because the opposite error hides the target the pass exists to find, the total equals the two parts, and the run states how many commits the default caught.
- **Nothing acts on churn alone.** A rewrite candidate carries the defect the rewrite would fix, and a high-churn file with no finding is named stable-but-evolving and stays off the list.
- **The ranking does not read as a defect list.** It is a prioritisation input whose meaning comes from finding density.

## When it runs

At each milestone start, and whenever a rewrite is proposed from a finding. The pass is a prioritisation instrument, not a gate: it runs when the tree has moved enough that the ranking would differ.

## Conventions

The pass follows the conventions of the files it touches: `task-list` governs a roadmap row's shape, and `work-log` governs a report's. Nothing it derives is committed.
