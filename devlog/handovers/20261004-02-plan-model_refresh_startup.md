# Handover - Plan: model-refresh at startup

## Objective

Interview the operator across the whole `model-refresh improvements` parent and turn the answers into decisions and roadmap rows. The interview's subject is the catalog fetch and merge as a state machine: whether its states and transitions are enumerated, documented, and tested, and whether the invariant catalog is accurate against them.

## Problem

The extension decides what the refresh produced from source counts, and it gates the persisted pi.dev catalog on a date comparison it misread. `stored.lastModified` is the publish time pi.dev serves in its `Last-Modified` header, not the time of any fetch, and `isStoreNewerThanBaked` compares it against the installed build's baked `generatedAt` (`catalog.ts:60`). Neither clock moves when the extension fetches, so the gate opens and closes for reasons unrelated to a refresh, and there are runs where a refresh changes nothing the message can see, and runs where the served catalog changes while the message does not.

Behind that defect is a modelling gap. The fetch and merge path was never enumerated as states and transitions, so the invariant catalog states only properties of the union given its inputs (M1-M8, U1-U4, G1-G3, L1-L2, C1-C4, T1-T4, W1, D1, N1-N2, R1) and no property of the sequence. `report.stored` is filled with the raw size of the persisted catalog (`refresh.ts:66`, `:104`) while admission is decided at `catalog.ts:233`, so a closed gate renders `store 469` beside a served catalog that took zero store entries. The lifecycle transitions - A14's pre-session refresh, the failing-source narrowing, and the pre-UI report hold (A13) - rest on direct assertions and a manual pty run, and nothing in the suite can falsify them.

## Decisions

1. **The session grain is one task that needs decisions before it can be worked** - the slicing of the `model-refresh improvements` parent. Not a milestone scope: T12 is a track, and its two standalone rows and its upstream row are outside this session's problem.
2. **The refresh path is modelled as three separate systems, not one machine with regions** (operator, 2026-10-04): the update producer, the catalog's own state machine with its own initial state and transitions, and the emitted actions. Separate systems make "nothing happened" and "something happened but was not applied" different observations.
3. **The update typology collapses to `absent`, `failed`, and information received**; the catalog classifies received information into `no-catalog-change` or `catalog-change`. Additive, revised and retractive stop being update types and become the catalog's processing detail; failures stay distinct because they announce differently.
4. **Actions are keyed on the transition's before/after catalog state, not the update's class**, and `catalog-change` is the full entry-state delta: `+n / -n` for id adds and removes, plus `m revised` when field-level revisions are nonzero. An id-set-only predicate would drop the exact class the extension was built to fix, which was `space-bunny-free` served with `kimi-k2.6`'s context window and pricing.
5. **The persistent `setStatus` footer row is dropped.** The reconciliation is relevant only at catalog-update or model-load time, so the surface is a one-shot announcement carrying the catalog diff rather than a permanently displayed line.
6. **`ModelSelectorComponent`'s refresh status line is not writable by an extension.** The three strings (`Refreshing model catalogs...`, `Model catalogs refreshed.`, `Could not refresh model catalogs: <error>`) are private literals in pi's interactive mode, and `RefreshModelsContext` (`pi-ai/dist/models.d.ts:13`) exposes `credential`, `stored`, `publish`, `allowNetwork`, `force` and `signal` with no status channel; `ModelsRefreshResult` carries only `aborted` and `errors`, so a provider can influence that line only by throwing. The announcement is therefore out of band, at a UI moment the extension owns.
7. **The announcement surface is `ctx.ui.notify(line)`** (operator, 2026-10-04): at `session_start` for the startup refresh, where it appends a dim line at the top of the transcript directly below the startup header, and on completion for a later refresh. No `setStatus` and no widget: `notify` is event-scoped, persists nothing, and needs no clearing logic. The `Model scope:` line itself is pi's pre-TUI `console.log` and is not writable; the extension puts its line as close to it as the API allows.
8. **The gate stays a mirrored pi policy and stops being an input to the message** (operator, 2026-10-04). `isStoreNewerThanBaked` keeps its predicate - the persisted entry is admitted while its remote publish time is later than the installed build's `generatedAt` - and becomes one named application policy in the catalog enumeration, with no claim about fetching. A11's `agrees with pi` case holds. The original defect closes by construction because the announcement is a function of the served catalog's before/after state, not of the gate.
9. **The three-system diagram is the extension's state-machine record and persists in `README.md`** (operator, 2026-10-04), as a new section. It is the enumeration the transition tests and the invariant audit are written against.
10. **The invariant-audit rule** (operator, 2026-10-04): every transition names at least one invariant or records why it has none; every invariant is exactly one of a state, transition, or policy property; every transition invariant gains a mutation row; the three lifecycle transitions (pre-session refresh, failure narrowing, pre-UI hold) gain ids and falsifiable cases; and a machine-run totality check asserts every transition id has a case and every case names a transition or state id.
11. **The `mergeCatalogs` key is fixed to pi's `type + id`** (operator, 2026-10-04). `buildUnion` indexes by `model.id` alone today (`catalog.ts:106`) while pi's `mergeModels` keys on type plus id, so a same-id, different-type pair merges here and stays two in pi - the one class where G2's `agrees with pi` case parts ways, and nothing constructs it. The fix is the index key, the pair added to G2, and a mutation row.
12. **The deferred-knowledge questions stay deferred knowledge tests in `README.md`, with no roadmap rows** (operator, 2026-10-04): A7's `glm-5.3-flash` case, the `kimi-k2.6` 403, and the `qwen3.6-plus` dual-adapter transport probe. They are resolved by the next reader who picks up the README, once the key or quota frees up. The `reasoning_effort: "none"` question is dropped: no code depends on it and the gateway's counts cannot settle it. A7's deepseek case is not a probe gap but a scope error - A7 is about gateway acceptance of the effort, and a format that emits none is outside its domain - so A7's text narrows with the audit.
13. **All invariants that hold no mutation row gain one, except R1** (operator, 2026-10-04). Measured: 13 labels hold no row, not the eleven the roadmap row claims - M4, M6, D1, G2, L1, L2, C2, C3, T1, T4, W1, M2, R1. Twelve gain a row; R1 is the bijection between the catalog and the test file, so mutating it would mutate the gate, and it is exempt with the reason recorded in the audit table.
14. **The `enabledModels` order rule lands in the extension's `README.md`** (operator, 2026-10-04), because the scope order is behaviour the extension extends: it supplies the catalog the resolver reads, so the rule about which entry supplies the default is the extension's to state. The default-model row loses its report and mitigation halves - the report is an upstream artifact, the mitigation has landed - and keeps only the rule statement.
15. **The two picker API gaps are upstream feature requests, recorded in the extension `README.md` as wanted-if-available and dropped as roadmap work** (operator, 2026-10-04): a provider-supplied refresh status string, and a per-model display badge a provider can set. Neither is reachable from an extension on the current API - `ModelSelectorComponent`'s status line is pi's private literal, and a row renders `id` and `[provider]` only - so pi is the only party that can supply them.
16. **The default-model report is not fixed upstream and does not become a deferred knowledge test** (operator questioned it; agent re-checked, 2026-10-04). `findInitialModel` is byte-identical between 0.87.1 and 0.99.2, the same four settings cases give the same four results against 0.99.2 and 1.0.0 (handover `20261002-09`), and the #9962 fix is scoped to an extension-registered native provider with a stored credential rather than a glob scope. Finding 1's first row - scope set, default present and authenticated - reproduces without any missing model; the missing-model case is the fourth row, not the first. The extension does not fix resolution, it supplies the catalog; our `enabledModels` head is a mitigation that masks the defect rather than closing it.
17. **The extension announces a discarded saved default rather than correcting the selection** (operator, 2026-10-04): option B of the three. At `session_start` it compares `ctx.model` against the saved default resolved through the scope (`ctx.getSettings()`), and emits the notify when the scope discarded a default that was applicable. It does not call `ctx.setModel`, so it reimplements no part of pi's resolution ladder and cannot disturb a resumed session's model, a `--model` override, or the cycle key. The removed cost is a local copy of one rule, dropped when pi fills `fallbackMessage` on that path.
18. **The union is not persisted today, and the extension is not restricted to pi's store** (measured, 2026-10-04). `runProviderRefreshPhase` calls `refreshModels` and discards its return value for persistence; only `context.publish({persist})` writes, and the extension never calls it. pi's own pi.dev overlay persists through `withRemoteCatalog`'s `context.publish({update, persist})`, which answers why the store has anything in it at all. The extension may keep its own cache file: nothing in `RefreshModelsContext` or the store API restricts a provider to `models-store.json`, and a file it owns is readable in `refreshModels`.
19. **The extension keeps its own catalog cache** (operator, 2026-10-04), so endpoint-sourced ids are present offline before pi's network refresh. It is a new declared source in System 1, read in the offline phase and additive only, with one write-back rule: a successful live fetch rewrites the cache wholesale, so a model the endpoint dropped disappears instead of being served forever from the union's remove-nothing property. It does not touch pi's store, so the gate's `lastModified` semantics and A11's agreement case are unchanged. Unit A's enumeration includes the source, and the invariant source model, the mutation catalog and the README all gain its cases.
